# 성능 측정

"빨라졌다"를 감이 아니라 숫자로 확인하기 위한 기록입니다. 모든 수치는 같은 조건에서 **이전 방식과 현재 방식을 나란히** 측정했습니다.

- 측정일 2026-11-08 · 헤드리스 Chromium · 1280×900 · 각 5회 중앙값
- 재현: `npm run bench` (측정용 Storybook 빌드 → Playwright 로 측정, [scripts/bench/run.mjs](../scripts/bench/run.mjs))
- 비교 화면은 배포된 Storybook 의 **Benchmarks** 메뉴에서 직접 볼 수 있습니다.

| 지표            | 측정 방법                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| React 렌더 시간 | `<Profiler>` 의 `actualDuration` 합계. 운영 빌드에서는 측정되지 않으므로 측정용 빌드만 `react-dom/profiling` 사용 |
| 스타일·레이아웃 | Chrome DevTools Protocol `Performance.getMetrics` 의 `RecalcStyleDuration`·`LayoutDuration` 변화량                |
| JS 힙           | 강제 GC 후 `JSHeapUsedSize`                                                                                       |
| 스크롤 프레임   | 250px 씩 80번 스크롤하며 매 단계 다음 animation frame 까지 걸린 시간의 p95                                        |

## 1. 대용량 목록 — 가상화 (`VirtualDataTable`)

같은 10,000행을 일반 표(`DataTable`)와 가상화 표(`VirtualDataTable`)로 그렸습니다.

| 항목               |  일반 표 | 가상화 표 |           차이 |
| ------------------ | -------: | --------: | -------------: |
| 화면에 그린 행     |   10,000 |        21 |              — |
| DOM 노드 수        |   60,012 |       136 | **441배 적음** |
| 첫 렌더 React 시간 | 730.1 ms |   12.7 ms |  **57배 빠름** |
| JS 힙              | 114.4 MB |    8.6 MB |  **13배 적음** |
| 스크롤 프레임 p95  |  18.0 ms |   18.8 ms |      거의 같음 |

### 측정으로 찾은 문제: 가상화했더니 스크롤은 오히려 느렸다

처음 측정했을 때 가상화 표의 스크롤 프레임 p95 가 **23.6 ms** 로 일반 표(18.0 ms)보다 나빴습니다.
일반 표는 이미 다 그려 두었기 때문에 스크롤이 브라우저만의 일인 반면, 가상화 표는 스크롤할 때마다 React 가 보이는 행을 다시 렌더링합니다.
이때 **새로 화면에 들어온 행뿐 아니라 이미 보이던 행까지 전부** 다시 렌더링하고 있었습니다.

→ 행·카드를 `React.memo` 컴포넌트로 분리해, props(행 데이터·위치)가 그대로인 행은 건너뛰게 했습니다.

| 스크롤 80단계 동안 | 메모이제이션 전 |      후 |           차이 |
| ------------------ | --------------: | ------: | -------------: |
| React 렌더 합계    |        247.4 ms | 99.0 ms | **2.5배 감소** |
| 프레임 p95         |         23.6 ms | 18.8 ms |   일반 표 수준 |

## 2. 다크 모드 전환 — CSS 변수 테마

버튼·칩·입력칸 각 300개가 있는 화면에서 모드를 1회 전환했습니다.

| 항목             | 테마 재생성 (이전) | CSS 변수 (현재) |            차이 |
| ---------------- | -----------------: | --------------: | --------------: |
| 클릭 → 화면 반영 |           566.2 ms |        148.3 ms |  **3.8배 빠름** |
| React 렌더 시간  |           103.8 ms |          0.0 ms | **리렌더 없음** |
| 스타일 재계산    |            62.1 ms |         62.3 ms |            같음 |

- 이전 방식은 모드가 바뀔 때마다 새 테마 객체를 만들어 내려보내므로, 테마를 쓰는 모든 컴포넌트가 다시 렌더링되고 Emotion 이 새 스타일을 만들어 넣습니다.
- CSS 변수 방식은 `<html data-color-scheme>` 속성만 바뀌고 변수 값이 교체되므로 **React 는 아무것도 다시 렌더링하지 않습니다.** 남는 비용은 브라우저의 스타일 재계산(두 방식 동일)뿐입니다.

## 3. 번들 크기 예산 (`npm run size`, CI 에서 초과 시 실패)

gzip 기준. 설정: [.size-limit.json](../.size-limit.json)

| 묶음                               |     현재 |   예산 |
| ---------------------------------- | -------: | -----: |
| 앱 진입 JS (React·라우터·MUI 코어) |  86.0 kB |  95 kB |
| 공유 청크 (MUI 컴포넌트·공통 UI)   | 107.9 kB | 120 kB |
| 목업 API (MSW)                     | 158.1 kB | 170 kB |
| 전체 JS (모든 페이지 청크 포함)    | 456.1 kB | 500 kB |

- 페이지는 라우트 단위로 나눠 처음 방문할 때 내려받습니다 (대시보드 1.2 kB, 환자 프로필 2.8 kB, 예약 폼 19.8 kB 등).
- **목업 API(MSW)가 전체의 약 35%** 입니다. 백엔드 없이 배포하기 위한 데모용이며, 실제 API 를 쓰면 `import.meta.env.DEV` 조건으로 제외되어 초기 로딩이 그만큼 줄어듭니다.

## 4. Lighthouse (`npm run lighthouse`, CI 에서 기준 미달 시 실패)

운영 빌드 · 데스크톱 프리셋 · 5회 중앙값. 기준: [lighthouserc.json](../lighthouserc.json)

| 페이지                | 성능 | 접근성 | 권장사항 | SEO |    LCP | CLS |
| --------------------- | ---: | -----: | -------: | --: | -----: | --: |
| 대시보드              |   83 |    100 |      100 | 100 | 0.92 s |   0 |
| 대시보드 (온결피부과) |   84 |    100 |      100 | 100 | 0.94 s |   0 |

- **측정으로 고친 것**: 처음 측정 때 권장사항 96 — `favicon.ico` 404 콘솔 오류, 알림 배지에 숨은 "0" 글자가 버튼 이름("알림")과 어긋나는 문제(label-content-name-mismatch) → 아이콘 추가, 읽지 않은 알림이 0 이면 배지 내용을 비움 → **100**
- 성능 점수는 69~98 로 편차가 커서 CI 에서는 경고만 합니다. 점수를 깎는 것은 Total Blocking Time(중앙값 약 350 ms)이며,
  Chrome 트레이스로 나눠 보면 앱 진입 JS 평가(약 70 ms) · 첫 React 렌더(약 100 ms) · 스타일·레이아웃(약 80 ms) 입니다.
  다음 개선 후보: 첫 화면에 필요 없는 MUI 컴포넌트 지연 로딩, 목업 API 시작을 첫 렌더와 병렬화.
